# Décisions techniques

Une ligne par décision : date, choix, raison.

- 2026-11-13 : SSH/SFTP via SSH.NET, terminal via xterm.js dans WebView2 (**remplacé le 2026-11-14**, voir plus bas), MVVM via CommunityToolkit.Mvvm — éviter de réécrire protocole et émulation de terminal.
- 2026-11-13 : .NET 10 (`net10.0`, SDK `10.0.x`) — dernière LTS active (.NET 8 est en fin de vie depuis le 2026-11-10, .NET 11 est une STS) ; le Windows App SDK stable (2.6.5) cible `net6.0-windows10.0.17763.0` et s'utilise donc tel quel avec .NET 10.
- 2026-11-13 : Windows App SDK 2.6.5 via le métapaquet `Microsoft.WindowsAppSDK` (et non les paquets composants un à un) — configuration officielle, moins de risque pour le mode non packagé auto-contenu, au prix de ~18 Mo inutilisés (IA, recherche, widgets) **Remplacé le 2026-11-14** : le métapaquet coûtait en réalité 65 Mo, voir plus bas.
- 2026-11-13 : `TargetFramework` de l'app = `net10.0-windows10.0.19041.0`, minimum Windows 10 1809 (17763) — valeurs du modèle WinUI 3 ; Mica n'apparaît que sous Windows 11.
- 2026-11-13 : tests avec `xunit.v3` sur Microsoft.Testing.Platform (`global.json` → `test.runner`) — le SDK .NET 10 n'accepte plus VSTest pour xunit.v3 ; commande : `dotnet test --project …`.
- 2026-11-13 : versions NuGet centralisées dans `Directory.Packages.props` — un seul endroit à mettre à jour.
- 2026-11-13 : chaînes de l'interface via une extension XAML `{l:Str Key=…}` adossée aux `.resw` plutôt que `x:Uid` — une clé absente affiche la clé au lieu de planter l'app au chargement de la page, et ça marche sur les propriétés attachées (accessibilité, info-bulles).
- 2026-11-13 : les pages sont créées une fois et masquées/affichées (pas de `Frame.Navigate`) — les terminaux et sessions SFTP ouverts survivent au changement de page.
- 2026-11-13 : mode `Quai.exe --smoke-test <dossier>` exécuté par le CI (x64) — seule façon de vérifier que l'app publiée démarre réellement et que chaque page se charge, faute de pouvoir la lancer à la main.
- 2026-11-13 : pas de trimming ni de fichier unique à la publication — WinUI 3 et les liaisons XAML s'appuient sur la réflexion ; un zip à décompresser suffit **Trimming : remplacé le 2026-11-14**, voir plus bas (toutes les liaisons sont en `x:Bind`, compilées, sans réflexion).
- 2026-11-13 : `ISecretStore` défini dans `Quai.Core`, implémenté dans l'app avec `PasswordVault` (ressource « Quai ») — `PasswordVault` est une API WinRT, la garder hors de Core laisse Core portable et testable ; le modèle `ConnectionProfile` n'a aucun champ secret, le JSON ne peut donc pas en contenir.
- 2026-11-13 : view-models dans `Quai.Core` (CommunityToolkit.Mvvm ne dépend pas de WinUI) avec `IDialogService` / `IStrings` implémentés par l'app — toute la logique du carnet est couverte par des tests xUnit sans interface graphique.
- 2026-11-13 : dossiers = simple chemin « A/B » porté par chaque connexion, filtres dossiers / tags dans un volet à gauche (pas d'arborescence glisser-déposer) — sobre, et un dossier disparaît tout seul quand il est vide.
- 2026-11-13 : interface forcée en `fr-FR` (`ApplicationLanguages.PrimaryLanguageOverride`) tant que seul le français existe — sinon les textes fournis par WinUI (boutons, menus) restent dans la langue de Windows.
- 2026-11-13 : `known_hosts` propre à l'app (`%LOCALAPPDATA%\Quai\known_hosts`) au format OpenSSH non haché, écrit par nos soins — aucune lib NuGet maintenue ne gère ce fichier, le format tient en une ligne par hôte ; comparaison stricte : toute clé différente de celle enregistrée pour `hôte:port` = « empreinte modifiée ».
- 2026-11-13 : clé d'hôte inconnue ou modifiée → la connexion est refusée dans le rappel SSH.NET (`CanTrust = false`), puis on demande à l'utilisateur et on se reconnecte — pas de boîte de dialogue bloquant le fil réseau (délais d'expiration), et la vérification n'est jamais contournée : la seconde connexion repasse par la même comparaison.
- 2026-11-13 : sans mot de passe en coffre, une première connexion « sonde » sans authentification valide la clé d'hôte avant de demander le mot de passe — même ordre qu'OpenSSH : on ne saisit rien pour un serveur non vérifié.
- 2026-11-13 : empreinte modifiée = alerte rouge, « Annuler la connexion » par défaut ; « Remplacer la clé enregistrée » reste proposé (serveur réinstallé) mais demande un clic volontaire.
- 2026-11-13 : terminal = xterm.js 6 + addon fit copiés dans `Assets/Terminal/vendor` (pas de CDN, CSP `default-src 'none'`), servis à WebView2 par un hôte virtuel local ; échanges en messages JSON, sortie en base64 (octets bruts, l'UTF-8 est décodé par xterm.js). **Remplacé le 2026-11-14.**
- 2026-11-13 : copier / coller du terminal via le presse-papiers Windows côté C# (Ctrl+C avec sélection, Ctrl+V, clic droit, comme Windows Terminal) — évite les demandes d'autorisation du navigateur embarqué.
- 2026-11-13 : le shell est lu par une boucle `ShellStream.Read` (et non l'événement `DataReceived`) — sinon le tampon interne de SSH.NET grossit sans fin sur les longues sessions.
- 2026-11-13 : tests d'intégration SSH contre un vrai OpenSSH (`tests/integration/start-sshd.sh`, job `integration` sur `ubuntu-latest`) ; sans variables `QUAI_TEST_SSH_*` ils sont ignorés — le protocole est testé pour de vrai, pas simulé.
- 2026-11-13 : SFTP via l'API asynchrone de SSH.NET (`UploadFileAsync` / `DownloadFileAsync` avec progression et `CancellationToken`) ; les transferts de dossiers, la suppression récursive et le cumul de progression sont dans `SftpTransferEngine`, au-dessus d'une interface `ISftpSession` — testable avec un faux serveur en mémoire et avec le vrai OpenSSH.
- 2026-11-13 : un transfert annulé ou en échec supprime le fichier partiel de destination — un fichier tronqué ne doit pas passer pour complet ; contrepartie : pas de reprise de transfert pour l'instant.
- 2026-11-13 : liens symboliques distants supprimés / renommés via l'entrée du dossier parent — SSH.NET résout les liens (realpath) avant d'agir sur un chemin, ce qui supprimerait la cible au lieu du lien ; dans une arborescence, les liens vers des dossiers ne sont pas suivis (boucles).
- 2026-11-13 : un seul transfert à la fois par onglet, file d'attente visible — une seule connexion SFTP par session, comportement prévisible ; le parallélisme pourra venir plus tard.
- 2026-11-13 : écrasement = une confirmation par lot (noms en conflit listés), suppression distante = toujours une confirmation, suppression locale = corbeille Windows (`Microsoft.VisualBasic.FileIO`, fourni avec .NET) plutôt qu'une suppression définitive.
- 2026-11-13 : glisser-déposer entre les deux panneaux et depuis l'Explorateur Windows vers le serveur ; pas de glisser du serveur vers l'Explorateur (demanderait des fichiers virtuels COM) — utiliser le panneau local ou le bouton « Télécharger ».
- 2026-11-13 : séparateur redimensionnable des panneaux = `GridSplitter` de `CommunityToolkit.WinUI.Controls.Sizers` — composant existant plutôt qu'un séparateur maison.
- 2026-11-13 : réglages dans `settings.json` (`ISettingsService`), appliqués et enregistrés à chaque modification, sans bouton « Enregistrer » — comportement des Paramètres de Windows ; le terminal suit le thème de l'application (pas de thème de terminal séparé pour l'instant).
- 2026-11-13 : police du terminal = champ libre avec suggestions (pas d'énumération des polices installées) — WinUI n'expose pas la liste des polices sans Win2D ; un aperçu montre aussitôt si la police existe.
- 2026-11-13 : page des réglages avec `SettingsCard` (`CommunityToolkit.WinUI.Controls.SettingsControls`) — rendu Windows 11 sans style maison.
- 2026-11-13 : volet de navigation compact sous 1400 px de large — l'explorateur à double panneau a besoin de la largeur ; le volet s'ouvre toujours par le bouton menu.
- 2026-11-13 : distribution par **installateur Inno Setup** (`Quai-Setup-x64.exe` / `-arm64.exe`, un seul fichier) en plus des zips portables, à la demande d'Alexandre — installation par utilisateur dans `%LOCALAPPDATA%\Programs\Quai` (aucun droit administrateur), raccourci du menu Démarrer, entrée de désinstallation dans Windows. Inno Setup plutôt que MSIX (resterait non packagé, pas de certificat requis) ou qu'un exécutable auto-extractible (démarrage lent, pas de désinstallation).
- 2026-11-13 : désinstallation = fichiers, raccourcis et cache retirés ; les données (`%LOCALAPPDATA%\Quai`) et les secrets du coffre ne sont effacés que si l'utilisateur le demande (question posée, « non » par défaut ; `/PURGE=1` en mode silencieux). Les secrets sont retirés par `Quai.exe --purge-secrets`, appelé par le désinstallateur.
- 2026-11-13 : le CI installe réellement l'installateur x64, exécute le test de fumée sur l'application installée, puis désinstalle et vérifie qu'il ne reste rien — seule façon de garantir l'installateur sans poste Windows sous la main.
- 2026-11-13 : exécutables non signés (pas de certificat de signature de code) — SmartScreen avertit au premier lancement ; à traiter si le projet est diffusé plus largement.
- 2026-11-14 : terminal = **moteur natif de Windows Terminal** (`Microsoft.Terminal.Control.dll`, API C `HwndTerminal` : analyse VT, tampon de 9001 lignes, rendu AtlasEngine DirectWrite / Direct3D) à la place de xterm.js + WebView2 — décision d'Alexandre : interdit absolu d'embarquer une application web cachée. C'est le moteur de Windows Terminal lui-même (licence MIT), rien n'est réécrit ; aucune bibliothèque .NET maintenue n'offre un émulateur natif complet pour WinUI 3.
- 2026-11-14 : DLL tirée du paquet NuGet `CI.Microsoft.Terminal.Wpf` 1.25 (republication des binaires du CI de Microsoft, signés Microsoft, x64 et arm64, CRT statique) par `PackageDownload` : le paquet est téléchargé sans être référencé (un `PackageReference`, même avec `ExcludeAssets="all"`, ferait embarquer WPF par sa référence de framework) et seule la DLL native de l'architecture publiée est copiée. Le paquet n'est pas publié par le compte Microsoft : le CI vérifie la signature Authenticode « Microsoft Corporation » et l'architecture de la DLL publiée.
- 2026-11-14 : pas le `TermControl` XAML de Windows Terminal — il cible le XAML système (UWP), incompatible avec WinUI 3. Intégration = fenêtre Win32 enfant de la fenêtre principale, recalée sur une zone XAML (`TerminalView`) à chaque passe de mise en page.
- 2026-11-14 : une fenêtre Win32 passe au-dessus du XAML (« airspace ») : le terminal est masqué pendant un dialogue modal (`DialogService`), sur une autre page ou un autre onglet ; les menus, info-bulles et le volet de navigation déplié en superposition sont découpés de sa région (`SetWindowRgn`).
- 2026-11-14 : clavier, focus, molette et presse-papiers par sous-classement de la fenêtre du moteur, comme le contrôle WPF de Microsoft ; raccourcis de Windows Terminal (`Ctrl+C` avec sélection, `Ctrl+Maj+C`, `Ctrl+V`, `Maj+Inser`, clic droit, `Ctrl+Maj+flèches / Pg.Préc / Pg.Suiv` pour l'historique) ; barre de défilement XAML à côté (le moteur n'en dessine pas).
- 2026-11-14 : modes « bracketed paste » et suivi de la souris lus dans le flux du serveur par un petit automate (`TerminalModeTracker`, testé) — le moteur ne les expose pas ; sert à encadrer un collage multiligne et à laisser clic droit et molette à vim / htop.
- 2026-11-14 : taille de police du terminal en points, comme Windows Terminal (12 par défaut) ; liste de polices transmise au moteur avec repli sur Cascadia Mono puis Consolas.
- 2026-11-14 : test de fumée du terminal = frappe simulée (messages `WM_CHAR`), lecture de l'écran par une sélection souris simulée, contrôle que la fenêtre native s'efface derrière un dialogue et en changeant de page ; captures par copie d'écran (`RenderTargetBitmap` ne voit pas les fenêtres natives).
- 2026-11-14 : fermeture de la fenêtre (`AppWindow.Closing`) = confirmation s'il reste des sessions connectées ou des transferts (bouton par défaut « Annuler » dès qu'un transfert serait interrompu), puis déconnexion propre de chaque onglet (`AppShutdown`, testé), bornée à 5 s pour ne jamais bloquer la sortie si un serveur ne répond plus.
- 2026-11-14 : fermer un explorateur SFTP pendant un envoi attend (5 s au plus) que le transfert annulé ait supprimé son fichier incomplet sur le serveur avant de couper la session — auparavant la session pouvait être fermée avant ce nettoyage.
- 2026-11-14 : vérification des mises à jour = une requête `GET` à `api.github.com/repos/memton80/quai-ssh/releases/latest` au démarrage (3 s après), sans jeton ; bandeau `InfoBar` si la release est plus récente ; échec réseau silencieux (journal) ; désactivable dans les réglages (`checkForUpdates`). Écrite à la main : c'est une seule requête — Octokit serait disproportionné, Velopack / NetSparkle remplaceraient l'installateur ou exigeraient un flux appcast.
- 2026-11-14 : comparaison des versions avec le paquet `Semver` (règles SemVer 2.0 : `1.2.0-ci.4` < `1.2.0`, `1.10.0` > `1.9.3`) plutôt qu'un comparateur maison ; le lien « Télécharger » est construit par l'application à partir de l'étiquette validée, jamais repris de la réponse réseau.
- 2026-11-14 : connexions **série** via `System.IO.Ports` (paquet officiel de .NET, 10.0.15 comme les `Microsoft.Extensions.*`) plutôt que `RJCP.SerialPortStream` — brique Microsoft maintenue avec le runtime. Son défaut historique (exception non rattrapable au débranchement d'un adaptateur USB) est corrigé dans .NET 10 (vérifié dans le code source : la boucle d'événements s'arrête sur `ERROR_ACCESS_DENIED` / `ERROR_DEVICE_REMOVED`) ; la fermeture, qui peut encore lever après un débranchement, est rattrapée.
- 2026-11-14 : terminal série = même onglet et même moteur que le SSH : `ITerminalSession` devient générique (`Quai.Core.Terminal`), `TerminalSessionFactory` aiguille selon le type de connexion. Lecture de `SerialPort.BaseStream` sur un fil dédié (ni l'événement `DataReceived`, ni les méthodes texte de `SerialPort`), écriture sur un second fil : à 9600 bauds, coller quelques kilo-octets prend des secondes et l'interface ne doit pas attendre.
- 2026-11-14 : réglages et comportement calqués sur PuTTY : 9600 bauds 8N1 sans contrôle de flux par défaut, DTR et RTS levés à l'ouverture (RTS laissé au contrôle de flux matériel s'il est choisi ; ignoré sur les ports virtuels qui n'ont pas ces lignes), « break » de 2/5 s envoyé depuis le menu de l'onglet (clic droit), Entrée envoie CR, ni écho local ni conversion des fins de ligne.
- 2026-11-14 : port choisi parmi `SerialPort.GetPortNames()` (registre Windows) ou saisi, limité à la forme `COMn` : c'est la seule qu'ouvre System.IO.Ports sous Windows. Pas de nom « parlant » (« USB-SERIAL CH340 ») : il demanderait WMI ou SetupAPI, à voir plus tard.
- 2026-11-14 : champs « port » et « vitesse » = `AutoSuggestBox` (ports détectés et vitesses usuelles en suggestions, saisie libre), comme le champ « Dossier » — et non `ComboBox` éditable : la capture du test de fumée a montré qu'une `ComboBox` avec `IsEditable` n'affiche pas la valeur liée à l'ouverture de la fiche.
- 2026-11-14 : connexion série = `"protocol": "serial"` + objet `serial` dans `connections.json` ; un carnet existant (sans `protocol`) reste en SSH. Une connexion série ne garde aucun champ SSH ni secret : les secrets d'une ancienne configuration SSH sont effacés du coffre à l'enregistrement. Pas de SFTP sur une connexion série.
- 2026-11-14 : tests du série sur de vrais ports virtuels : `socat` (pseudo-terminal relié à `cat`, un « appareil » qui renvoie ce qu'il reçoit) ouvert par System.IO.Ports dans le job Linux d'intégration — écho, gros collage, réouverture, appareil qui disparaît ; le test de fumée Windows ouvre un onglet série de démonstration (bannière, écho, réponse au break).
- 2026-11-14 : **releases automatiques** — la version se prépare dans `Directory.Build.props` ; quand un numéro sans tag arrive sur `main`, le job `version` du CI le détecte (tags comparés sans tenir compte de la casse du « v »), le même run construit cette version, puis `softprops/action-gh-release` (déjà utilisé) crée le tag `vX.Y.Z` et la release. Plutôt que release-please / semantic-release : leurs règles « feat = version mineure » auraient donné 1.1.0 au lieu du 1.0.1 voulu, release-please impose une PR de release à fusionner, et un tag créé par le jeton du workflow ne relance pas le workflow (il faudrait un jeton personnel). Raison du changement : le tag `V1.0.0` (V majuscule) posé à la main ne correspondait pas au filtre `v*`, la 1.0.0 n'a jamais été publiée.
- 2026-11-14 : **mesures avant d'optimiser** — le résumé de chaque run CI donne la taille installée, celle de l'installateur et du zip, et les fichiers les plus lourds ; le test de fumée relève le temps jusqu'au premier rendu (journalisé aussi à chaque lancement), la mémoire, les fils et les handles à quatre moments du parcours (`smoke-metrics.md`). Référence de la 1.0.1 (x64) : 253 Mo installés, installateur 69 Mo, zip 95 Mo.
- 2026-11-14 : Windows App SDK par **composants** (`Base`, `Foundation`, `InteractiveExperiences`, `WinUI`, même version via `WindowsAppSdkVersion`) au lieu du métapaquet — le métapaquet ajoutait l'IA, le ML (onnxruntime 23 Mo, DirectML 19 Mo), la recherche sémantique, les widgets et DWriteCore : 65 Mo jamais chargés (vérifié : aucune DLL gardée ne les importe). Le paquet `Microsoft.WindowsAppSDK.Runtime` (172 Mo à télécharger) ne sert qu'au mode dépendant du framework, il est retiré aussi ; la projection WebView2 est alors demandée explicitement (`WebView2EnableCsWinRTProjection`), son choix automatique dépendant de ce paquet.
- 2026-11-14 : publication allégée par des cibles MSBuild (et non en effaçant des fichiers après coup, pour que `Quai.deps.json` reste exact) : langues de WinUI limitées au français et à l'anglais (`MicrosoftWindowsAppSDKFilesExcluded`, prévu par le Windows App SDK), ni `map.html` (MapControl), ni WebView2 natif (`Microsoft.Web.WebView2.Core.dll`, `WebView2Loader.dll` : aucun WebView2 dans Quai), ni outils de diagnostic du runtime (`createdump`, `mscordbi`, `mscordaccore`, `DiaSymReader`, retirés à la publication seulement pour garder le débogage dans Visual Studio). Les `.pdb` restent : numéros de ligne dans les journaux d'erreur. Le CI refuse ces fichiers s'ils reviennent.
- 2026-11-14 : compression maximale — Inno Setup `lzma2/ultra64` (dictionnaire de 64 Mo, archive solide), zip `-mx=9`.
- 2026-11-14 : **trimming à la publication** (`PublishTrimmed`, `TrimMode=partial`) — l'hypothèse du 2026-11-13 ne tenait pas : les 129 liaisons XAML sont toutes en `x:Bind` (compilées), et le JSON passe désormais par un contexte généré (`QuaiJsonContext`, testé contre l'ancien format). Mode partiel : seules les bibliothèques déclarées compatibles sont réduites (runtime .NET, projection du SDK Windows de 25 Mo, WinUI, SSH.NET, Serilog, DI…) ; BouncyCastle et le Community Toolkit restent entiers, la cryptographie SSH n'étant pas exercée par le test de fumée. L'interop WinRT reste entière (`WinRT.Runtime`, `Microsoft.Windows.SDK.NET`, `Microsoft.WinUI`, projections `*.Projection`, `TrimMode=copy`) : les view-models et collections de Quai.Core passent à WinUI par des interfaces COM que CsWinRT construit par réflexion (Quai.Core, sans Windows, n'a pas son générateur) ; réduites, ces assemblies faisaient planter le carnet dès l'affichage (vu par le test de fumée). `EventSourceSupport` et `HttpActivityPropagationSupport` désactivés (inutiles).
- 2026-11-14 : **démarrage après trimming** — le trimming réécrit les bibliothèques et leur retire leur code précompilé : premier rendu d'environ 700 à 1 300 ms. Mesure dédiée au CI (`--startup-probe`, trois lancements : le premier paie aussi l'analyse antivirus des fichiers non signés). Retenu : `PublishReadyToRun` guidé par le profil standard de .NET (`StandardOptimizationData.mibc`, livré avec le runtime) et `System.Private.CoreLib` gardé dans sa version officielle (+2 Mo d'installateur) ; SDK Windows, WinUI, WinRT.Runtime, projections et BouncyCastle non précompilés (inchangés). Lancements habituels (x64, CI) : environ 610 ms, contre 700 sans trimming et 750 avec CoreLib réduit. Le lancement manuel du workflow accepte des propriétés MSBuild d'essai (`publish_args`, jamais publiées en release) pour refaire ces comparaisons.
